# Как собирать из дизайн-системы

Правила для человека. Та же логика, что в [`../04-агенты/AGENTS.md`](../04-агенты/AGENTS.md) — там она для ИИ-агентов, здесь как читать и применять самому.

## Главное правило

**Макет задаёт структуру и тексты. Внешний вид задаёт дизайн-система.**

Прототип собирается из компонентов ДС: классы `ds-*` из `components-web/components/<Имя>_DS/*.css` и токены `--ds-*` из `components-web/tokens.css`. Из макета берём, **что** на экране и в каком порядке; **как** это выглядит, решает система.

Что не переносим из макета на компоненты: капс, цвета, трекинг, радиусы, внутренние отступы и размеры. У компонента свои токены и свои состояния — если поставить ему макетные значения, он перестанет совпадать с остальной системой.

## Что допустимо и что нет

| Допустимо | Недопустимо |
|---|---|
| Обвязка раскладки: позиционирование, ширины колонок, гэпы контекста | Свои классы вида `.my-row`, `.card-fix` вместо компонента |
| Правка поверх ДС при **реальном пробеле** системы, с комментарием `/* косяк ДС: … */` | Тихая правка «под макет», без пометки и без записи в список замечаний |
| Новый компонент, если такого в ДС **нет** — с пометкой и записью в подсказки | Дублирование компонента ради одного экрана |
| Настройка компонента через его переменные `--ds-…` | Переписывание стилей компонента целиком |

## На что смотреть в первую очередь

- **Больше одного атома → ищи групповой компонент ДС** (заказчик, 15.10.2026: «Если компонента-атома используется больше 1 шт — ищи групповой компонент. Если группового компонента нет, то всё равно должен быть отступ между компонентами»). Две и более кнопки — `ds-btn-group` (`ds-btn-group--horizontal`, в футерах ещё `--margins`), чипы — `ds-chips-group`, иконки-кнопки — `Button icon group`; зазор — только токеном группы (`--ds-button-group-gap` и т. п.): свой `gap`/`margin` не задавать. Порядок кнопок: второстепенные слева, главная последняя справа. Если группового компонента в ДС нет — между атомами **всё равно обязателен отступ** (gap из токенов ДС), вплотную не ставить.
- **Демо-контент удаляем — остаётся только свой** (заказчик, 16.10.2026). Демо-страница — шаблон-подложка: взяв её, заменяем ВСЁ содержимое шаблона своим (контент, экраны, пункты селекта «Экраны», демо-примеры); демо-контент в готовой странице не остаётся.
- **Состояния берём из ДС:** Default / Hover / Press / Selected / Disable — не придумываем свои цвета и тени.
- **Иконки** — Material Icons по имени (`<span class="material-icons">search</span>`), семейство Outlined. Фирменные глифы — точной выгрузкой из макета, инлайн svg с `fill: currentColor`.
- **Сначала спецификация, потом вёрстка.** Перед сборкой блока читаем `components-web/iiko-ds-spec.md`: там описано, какие варианты бывают и как называются классы.

## Раскладка против компонента

Частая ошибка — «докрутить» компонент раскладкой соседнего блока: задать ему ширину, высоту, отступы «чтобы влезло». Раскладка имеет право располагать компонент (в колонке, в строке, с гэпом контекста), но не имеет права менять его внутреннюю геометрию. Если компонент не влезает — это вопрос к раскладке или к самой системе, а не к его паддингам.

**Ширина компонента — по блоку.** Каждый компонент растягивается по ширине блока, в котором стоит (колонка формы, карточка, панель): ширину задаёт раскладка, а не содержимое. Компонент, оставшийся уже своего блока (например, поле или блок с чипами не на всю ширину формы) — ошибка сборки.

## Порядок работы над блоком

1. Прочитать спецификацию по нужным компонентам.
2. Собрать блок из компонентов и токенов.
3. Проверить состояния и поведение при разных размерах (на мобильном — отдельно).
4. Пройти чек-лист из [`../прототипы/readme.md`](../прототипы/readme.md).
5. Если чего-то в системе нет — не «дорисовать», а зафиксировать пробел: он попадёт в список замечаний к ДС.
